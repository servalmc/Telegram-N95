# Окружение сборки

Проверено на Windows 11 Pro x64 (сборка 26200), август 2026.

## Установленные компоненты

| Компонент | Версия | Расположение |
| --- | --- | --- |
| S60 3rd Edition FP1 SDK for Symbian OS, C++ | 1.0.1 | `C:\Symbian\9.2\S60_3rd_FP1` |
| CSL ARM Toolchain (GCCE) | GCC 3.4.3, CodeSourcery ARM Q1C 2005 | `C:\Program Files (x86)\CSL Arm Toolchain` |
| ActivePerl | 5.6.1 build 635 | `D:\Perl` |
| Инструменты реестра устройств Symbian | — | `C:\Program Files (x86)\Common Files\Symbian\tools` |

Дистрибутивы всего перечисленного лежат в архиве
[archive.org/details/nokia_sdks_n_dev_tools](https://archive.org/details/nokia_sdks_n_dev_tools);
исходный сайт Forum Nokia давно закрыт.

Переменные окружения заданы на уровне пользователя: `EPOCROOT=\Symbian\9.2\S60_3rd_FP1\`,
а каталоги инструментов добавлены в `PATH`.

## Сборка

```
tools\build.bat              REM GCCE release, для устройства
tools\build.bat gcce udeb    REM GCCE debug
tools\build.bat winscw udeb  REM эмулятор
tools\package.bat            REM упаковка и самоподпись
```

## Неочевидные особенности платформы

Каждая из них проявляется сообщением об ошибке, которое уводит в сторону от настоящей причины.

**Собирать только из `cmd.exe`, не из PowerShell.** Каждый инструмент SDK — это лаунчер
на 45 КБ, запускающий одноимённый `.pl` скрипт и не заключающий путь к нему в кавычки.
`cmd.exe` использует записи `PATH` дословно, поэтому короткие пути 8.3
(`C:\PROGRA~2\COMMON~1\Symbian\tools`) снимают проблему пробелов. PowerShell же
разворачивает короткий путь обратно в длинный перед запуском, пробелы возвращаются,
и получается `Can't open perl script "C:\Program": No such file or directory`.

**Perl должен быть именно 5.6.1.** `abld` и `bldmake` — это Perl-скрипты, которые
на современном Perl не работают.

**`EPOCROOT` не содержит буквы диска** и разрешается относительно текущего, поэтому проект
на `D:` не соберётся против SDK на `C:`. Вместо переустановки сделан junction `D:\Symbian`,
указывающий на `C:\Symbian`: junction'ы прозрачны для разрешения путей, поэтому сборка
видит согласованные пути на `D:`, а пишет фактически на `C:`. Проверено сборкой одного
и того же примера с обоих дисков.

**`set` в bat-файле захватывает завершающие пробелы.** Запись `set EPOCROOT=\путь\ && cmd`
присваивает `"\путь\ "`, после чего инструменты жалуются, что `EPOCROOT must end with a
backslash`. Всегда использовать форму в кавычках: `set "EPOCROOT=\путь\"`.

**Наложить vista-патч.** Он заменяет `Epoc32\tools\cl_bpabi.pm` — модуль, генерирующий
мейкфайлы GCCE, — и нужен на всём, что новее Windows XP. Оригинал сохранён рядом
как `cl_bpabi.pm.orig`.

**`makesis` не раскрывает `$(EPOCROOT)`** в этой версии SDK, это появилось в более позднем
инструментарии. Поэтому пути в пакете записаны от корня диска, например
`\Symbian\9.2\S60_3rd_FP1\epoc32\release\gcce\urel\...`, что заодно корректно работает
через junction.

**SVG-иконки не собираются.** `mifconv` передаёт преобразование SVG в SVGB программе
`svgtbinencode.exe`, а в этом SDK она есть только как бинарник эмулятора в
`Epoc32\release\winscw\udeb`. Запущенная отдельно, она завершается с кодом 0 и молча
ничего не создаёт, после чего `mifconv` падает с `Unable to open file for reading! ...svgb`,
и шаг `RESOURCE` обрывает сборку. Всё остальное компилируется и линкуется штатно.
Сам `mifconv` исправен и работает с исходниками BMP, которым нужен парный файл маски
`<имя>_mask_soft.bmp`.

**Эмулятор не проверялся.** WINSCW требует 32-битную Java 5 для своих диалогов настроек
и, по имеющимся сведениям, ненадёжен на современной Windows. На сборку под устройство
через GCCE это не влияет.
