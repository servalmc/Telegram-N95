# Техническое исследование и архитектурные решения

Этап 1 из плана разработки: проверка принципиальной совместимости MTProto и
Telegram API с Symbian 9.2 на Nokia N95 8GB.

Проверено по составу установленного SDK (S60 3rd Edition FP1) и документации
платформы. Выводы, помеченные как требующие замеров, на устройстве пока не проверялись.

## Краткий вывод

Реализация MTProto на этой платформе возможна, но **только с библиотекой Open C**.
Публичного SDK для этого недостаточно. Главная нерешённая проблема — не Telegram,
а обновление через GitHub: платформа не умеет TLS нужной версии.

## 1. Криптография

MTProto 2.0 требует: RSA-2048 без дополнения, Diffie-Hellman на 2048 бит,
AES-256 в режиме IGE, SHA-1, SHA-256, криптостойкий генератор случайных чисел
и разложение числа `pq` на множители.

Что даёт публичный SDK:

| Компонент | Наличие |
| --- | --- |
| `hash.h` — MD2, MD5, SHA-1 | есть |
| `random.h` — генератор случайных чисел | есть |
| SHA-256 | **нет** |
| AES, RSA, длинная арифметика | **нет** (закрытый API `cryptography.dll`) |

Open C (плагин для 3rd Edition и FP1) содержит `libcrypto` из **OpenSSL 0.9.8a**,
которая закрывает все потребности: AES, SHA-256, RSA, длинную арифметику `BIGNUM`
для Diffie-Hellman и `RAND_bytes`. Из OpenSSL по экспортным ограничениям вырезаны
RC5, IDEA, Blowfish, CAST, RIPEMD, MD4, MDC2 и вся эллиптическая криптография —
**ни один из этих алгоритмов MTProto не использует**.

Режим IGE придётся реализовать самостоятельно поверх блочных примитивов
`AES_encrypt` и `AES_decrypt`: в OpenSSL его нет, он существует только в форке Telegram.
Это около сотни строк кода и хорошо покрывается тестами на официальных векторах.

**Решение:** Open C — обязательная зависимость проекта.

## 2. Сетевой транспорт

MTProto не использует TLS: у протокола собственное шифрование поверх обычного TCP.
Это принципиально важно, потому что системные защищённые сокеты Symbian 9.2
поддерживают только SSL 3.0 и TLS 1.0. Для Telegram достаточно `RSocket` из `es_sock.h`,
и ограничение платформы по TLS на работу клиента не влияет.

Для требований ТЗ по выбору точки доступа и экономии трафика в SDK есть всё нужное:
`commdb.h` и `commdbconnpref.h` для выбора точки доступа, `rconnmon.h` для
отслеживания состояния соединения.

## 3. Обновление через GitHub — главное ограничение

`api.github.com` и `objects.githubusercontent.com` требуют TLS 1.2 и выше.
Системный стек Symbian 9.2 этого не умеет, поэтому **обратиться к GitHub напрямую
средствами платформы нельзя**. Это ограничение не Telegram, а именно механизма обновлений.

Возможные пути:

1. **Встроить mbedTLS в приложение** и реализовать собственный TLS-клиент только для
   проверки обновлений. Полностью автономно, не требует ничего от пользователя,
   но добавляет заметный объём кода и увеличивает размер пакета.
2. **Промежуточный HTTP-эндпоинт**, отдающий манифест версии и файл по обычному HTTP,
   с GitHub как источником истины. Реализуется быстро, но требует своего хостинга
   и снижает безопасность канала обновления.
3. **Системный патч TLS 1.2** (порт mbedTLS с заменой `ssl.dll`) существует и активно
   поддерживается, но требует ROMPatcher+ и патча Open4All, то есть модифицированного
   телефона. Как обязательное требование к пользователю неприемлемо.
4. **Ручная установка**: приложение лишь показывает, что вышла новая версия,
   а пользователь скачивает `.sisx` на компьютер. Но и для проверки версии нужна сеть.

**Принято в коде 0.2.18:** GitHub — источник истины (публичный репозиторий и
Releases). С телефона проверка идёт обычным HTTP: `api.github.com` и CDN
отвечают редиректом на HTTPS, который N95 не умеет. Поэтому скачивание
`.sisx` остаётся на компьютере, а приложение находит уже скопированный пакет
и запускает установщик. Встраивать mbedTLS ради одного GET не стали.

## 4. Локальное хранилище

В ТЗ упомянут SQLite, однако `RSqlDatabase` появился только в Symbian 9.3
(S60 3rd Edition FP2) — в нашем SDK заголовка `sqldb.h` нет. Доступны два варианта:

- штатная Symbian DBMS (`d32dbms.h`) — есть в системе, но API громоздкий и слабо
  подходит под объёмы переписки;
- **сборка SQLite из амальгамации поверх Open C** — SQLite это переносимый C,
  а Open C даёт нужный POSIX-слой файлового ввода-вывода.

**Принято: SQLite поверх Open C.** Open C и так подключается ради криптографии,
а привычный SQL заметно упрощает работу с историей переписки.

Требует проверки на устройстве: блокировки файлов и `fsync` на Symbian ведут себя
не так, как в POSIX. Если поведение окажется ненадёжным, запасной путь — собственный
VFS-слой SQLite поверх `RFs` и `RFile` вместо POSIX-обёрток Open C.

## 5. Упаковка и зависимости

Open C стал частью прошивки только с FP2. На Nokia N95 8GB (FP1) его в ROM **нет**,
поэтому рантайм Open C нужно встраивать в наш `.sisx` вложенным пакетом, иначе
приложение не запустится у пользователя.

Итоговый состав зависимостей:

| Зависимость | Назначение | Как поставляется |
| --- | --- | --- |
| Open C (`libcrypto`, `libc`) | криптография MTProto, POSIX-слой для SQLite | вложенный пакет в нашем `.sisx` |
| SQLite | локальная база переписки | собирается в составе приложения из амальгамации |

Актуальное состояние: Open C и SQLite в сборку не вошли, криптография своя,
хранилище — файлы. mbedTLS для обновлений тоже нет (см. раздел 3).

## 6. Права и подпись

Запрашиваемые права — `NetworkServices`, `ReadUserData`, `WriteUserData`,
`UserEnvironment` — относятся к выдаваемым пользователем, поэтому самоподписанный
пакет остаётся работоспособным и Symbian Signed не требуется.

## 7. Открытые вопросы

- Производительность Diffie-Hellman на 2048 бит на ARM11 332 МГц: влияет на время
  холодного старта, ограниченное восемью секундами. Нужен замер на устройстве.
- Условия Telegram на получение `api_id` и `api_hash` для стороннего клиента.
- Секретные чаты требуют отдельной реализации end-to-end шифрования и вынесены
  в самостоятельный этап.
- Объём оперативной памяти под кэш переписки на устройстве с учётом лимитов процесса.
